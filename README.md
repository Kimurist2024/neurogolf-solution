# neurogolf-solution

Kaggle コンペ [The 2026 NeuroGolf Championship](https://www.kaggle.com/competitions/neurogolf-2026) の解法一式。

ARC-AGI の各タスク変換を再現する「できるだけ小さい」ニューラルネットを ONNX で作り、
`score(task) = max(1, 25 - ln(cost))`(cost = パラメータ数 + メモリフットプリント)を最大化する。

## 最終結果

- **最終スコア: 8025.82**
- 提出物: [submission.zip](submission.zip)(各タスク最大1ファイル `task001.onnx`〜`task400.onnx`)

| 指標 | ベースライン | 最終 |
|---|---|---|
| 合計スコア | 6347.82 | **8025.82** |
| コスト中央値 | 15,230 | **124** |
| コスト平均 | 29,727 | — |
| cost ≤ 100 のタスク | — | **174 / 400** |

## スコアリングの要点

- 正しさは全か無か: `train` + `test` + `arc-gen` の全ペア + 非公開ベンチで全セル完全一致して初めて得点
- cost は ln で効くため、構造の簡素化(オーダー削減)が重要
- ONNX 制約: 静的形状必須 / 禁止オペ(Loop, Scan, NonZero, Unique, Script, Function) / 1ファイル最大 1.44MB

---

## 改善の方針

6347 から 8025 までの過程で、方針は 4 回変わっている。順に、何を問題だと考え、それをどう潰したかを記す。

### 0. 前提: どこにギャップがあるのかを先に測る

最初にやったのは最適化ではなく**現在地の測定**だった。全 400 タスクのコスト分布を出すと、
平均 29,727 / 中央値 15,230。一方、上位陣のスコアから逆算される平均コストは約 314。
つまり我々のグラフは **50〜100 倍重い**。

この数字が方針を決めた。数個のパラメータを削る差分最適化では絶対に届かない。
`score = 25 - ln(cost)` は **cost を e 倍(約 2.7 倍)削って +1 点**なので、
+1600 点を狙うということは全タスクで**桁単位の構造圧縮**が要るということになる。

「ローカルのスコアラが壊れているのでは」という疑いも先に潰した。すでに 25.00 点のタスクが
存在した以上、スコアラの実装は正しく、**純粋に圧縮が足りていない**と確定させてから先に進んだ。

### 1. 学習をやめる

当初はニューラルネットを学習させてタスク変換を近似する路線だった。これを捨てた。

Discussion を横断して読むと、上位帯は **NN を学習させていない**ことが分かった。
多くのタスクは変換が全データで定数的であり、上位陣はそれを**ゼロパラメータの純関数型
テンソルプログラム**としてタスクごとに書き下していた。学習ベースの試みは軒並み失敗している。

そこで方針を「**タスク生成器の仕様をコンパイルする**」に変更した。
可視例は仕様を確認するためのフィクスチャであって、フィットする対象ではない、と位置づけを変えた。
これは後の事故対策(§4)にも直結する。

### 2. コストの本体を特定し、そこだけを狙う

公式スコアラを読み込み、コストの内訳を確定させた。

- `cost = パラメータ数 + 中間テンソルのメモリ`
- **`input` と `output` は計上されない**。それ以外のノード出力テンソルは全部計上される
- 各テンソルは `要素数 × dtype バイト数`、かつ静的宣言値と ORT 実測値の**大きい方**が採られる

ここから支配項が見えた。**float32 の `[1,10,30,30]` 中間テンソル 1 個で 36,000 バイト**。
つまり「10 チャンネルの one-hot を中間に持つかどうか」がほぼ全てだった。

この一点に対して効く型を整理したのが [docs/golf/ONNX_GOLF_PLAYBOOK.md](docs/golf/ONNX_GOLF_PLAYBOOK.md)。中核は次の 4 つ。

| 手 | 内容 |
|---|---|
| **出力を無料にする** | 10ch one-hot を実体化せず、単一チャンネルのラベル格子を持ち回り、最後の `Equal(lab, arange)` を**グラフ出力そのもの**にする。出力は計上されないので 0 バイト |
| **早期にチャンネルを潰す** | 重み `[0..9]` の 1×1 Conv で 10ch を色 ID の 1ch 格子へ落とし、空間処理は全て `[1,1,H,W]` で行う |
| **入力に上書きする** | 出力 ≒ 入力のタスクは `Where(mask, color, input)`。`input` は無料なので中間バッファが要らない |
| **dtype を落とす / 早期クロップ** | マスクは bool・uint8、算術は必要な op の直前でのみ int32・fp16 に広げる。生成器のサイズ上限までクロップしてから処理し、最後に `Pad` で戻す |

同時に**やっても無駄なこと**も確定させた。ORT 1.24 + `ORT_DISABLE_ALL` での
dtype/op サポート表を作り(1 バイト算術は存在しない、`OneHot` に整数カーネルが無い、等)、
ワーカーが同じ失敗を再発見しないようにした。

### 3. 「全体一括」から「1 タスクずつ」へ

最初は全 400 タスクに一括で効く**挙動を変えない変換**から入った
(未使用 initializer 削除、重複 initializer の統合、stale な `value_info` 削除、
no-op ノード除去、選択的な FP16/BOOL 化)。リスクゼロで確実に効く。

しかしこれは **+3 点規模で頭打ち**になった。当然で、これらはグラフの構造を変えないからだ。
ln の効くスコアで意味のある差を作るには構造そのものを設計し直すしかない。

そこで **1 タスク = 1 エージェント**の個別最適化に主軸を移し、それを工場化した
([proposals/003](proposals/003-per-task-golf-factory.md), [004](proposals/004-overnight-factory.md))。

```text
キュー(cost 降順)
   ↓
ブリーフ生成: グリッド可視化 + 現ネットの解剖 + 目標コスト
   ↓
ワーカー: 生成器仕様を読む → numpy 参照実装 → 最小 ONNX へ翻訳 → 反復
   ↓
ゲート: try_candidate.py だけが昇格経路
   ↓
マージ → 改善があれば即提出(1 タスクだけの改善でも提出する)
```

運用上、効いた判断は 3 つある。

- **昇格経路を 1 本に絞る** — 検証を通った ONNX ファイルだけが採用される。
  ワーカーの自己申告や「改善しました」という報告には採用経路が存在しない
- **バリア同期をやめる** — ウェーブ方式(全員終わるまで待つ)は待ち時間が無駄な上、
  セッションが落ちると全部消える。終わったワーカーから次のタスクへ流す連続キューにし、
  プロセスをセッションから切り離した
- **止め時を明文化する** — f32 Conv 出力の `[1,1,30,30]` = 3600 バイトのような
  **構造的な床**に当たったら、そこから先は 400 バイト(≒ +0.03 点)を削るために
  正しさのリスクを取ることになる。床に到達したら止める、と規約に書いた
  ([docs/golf/AGENT_LOOP_TASK_RULES.md](docs/golf/AGENT_LOOP_TASK_RULES.md))

### 4. 本当の敵は「ローカル合格 ≠ 本番合格」だった

中盤以降、点を失う原因は圧縮の失敗ではなく**通ったはずのネットが本番で 0 点になること**に移った。
ここが最も時間を使った部分で、失敗を 3 系統に分離したのが転換点になった
([docs/golf/ERROR_PATTERNS.md](docs/golf/ERROR_PATTERNS.md))。

| 系統 | 症状 | 対策 |
|---|---|---|
| **A: グレーダー処理エラー** | 該当タスクだけでなく**提出 zip 全体が無効化**される。ローカル 4 ゲート全通過でも起きる | 事前検知は不可能。エラー通知が犯人タスクを名指しするので、そのタスクだけベースに戻して即再提出 |
| **B: 非公開ベンチ乖離** | 提出は成立するが、投影スコアを大きく下回る | 原因は例フィット・高コスト帯の過剰削減など。生成器から**新規生成したデータでの全一致検証**(fresh ゲート)を必須化 |
| **C: fresh ゲートの誤判定** | 正しいネットが少数の失敗で弾かれる | fresh の REJECT は「過学習の確定診断」ではなく**リスク信号**として扱い、隔離して LB で実測判定する |

とくに重要だった知見が 2 つある。

**例フィットは必ずバレる。** 可視例に合わせた決定木ネットは、ローカル全合格でも
非公開ベンチで 0 点になり、実測で約 −15 点を失った。以降「仕様コンパイル限定・例フィット禁止」を
不変規程にし、ワーカーに provenance(仕様由来か否か)の申告を義務づけた。
座標定数・色定数・オブジェクト数の固定など、生成器から導けない定数は一切禁止した。

**退行したら二分探索ではなく計算で犯人を出す。** 束で提出して投影を下回ったとき、
乖離したタスクは本番で 0 点になり、見込んでいたスコアを丸ごと失う。つまり

```text
ギャップ = 局所推定スコア − 実測スコア ≒ 犯人タスクの new_score
```

が成り立つ。変更したタスクを `|new_score − ギャップ|` の昇順に並べれば、
**提出を 1 回も余分に使わずに犯人が特定できる**。実際、ギャップ 15.55 に対して
`new_score 15.542` のタスクが一意に一致し、そのタスクだけ戻して復旧した。

これに合わせて提出フローも「安全版 → リスキー版 →(必要なら)修正版」の**最大 3 提出**に固定した。
Kaggle は最良提出を保持するため、リスキー版が外れても LB は無傷で、判定だけが得られる。

### 5. 結果

最終的にコスト中央値 124、400 タスク中 174 件が cost ≤ 100、
最大コストのタスクでも 7,977(ベースラインの最大は 109,037)。
スコア 25.00 に到達したタスクも複数出た。

振り返ると、効いたのは個々の ONNX テクニックそのものよりも、
**測ってから方針を決めたこと**と、**失敗の系統を分離して各々に別の対策を当てたこと**だった。
